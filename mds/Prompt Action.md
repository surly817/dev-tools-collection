# 技术指北

`````` markdown
# 一、认知定位（Why & What）// 宏观认知：是什么、为什么存在、核心特征
## 1. 背景与起源：诞生的驱动力、解决的核心问题
## 2. 核心本质：最简化的核心模型（抽象本质）
## 3. 定位与关系：在技术体系中的位置、与同类事物的对比（替代/互补关系）

# 二、原理支撑（How - Theory）// 微观原理：内部结构、运行逻辑、抽象建模
## 1. 体系结构：核心组件、组件关系、整体架构图
## 2. 核心机制：支撑运行的关键原理（如调度机制、容错机制）
## 3. 抽象建模：如何将现实问题转化为技术模型（建模逻辑、核心抽象概念）
## 4. 流转逻辑：数据/信息/指令的传递路径与触发条件

# 三、实践应用（How - Practice）// 落地执行：从基础到复杂场景的应用
## 1. 基础操作：最小可用技能集（安装、配置、核心API）
## 2. 典型案例：代表性场景的完整实现（含步骤与解析）
## 3. 问题诊断：常见错误、异常排查与解决方案
## 4. 场景扩展：从单一场景到复杂系统的应用进阶

# 四、深度进阶（Mastery）// 精进与拓展：从熟练到精通
## 1. 性能优化：瓶颈分析、调优策略、最佳参数配置
## 2. 稳健性设计：容错机制、高可用方案、灾备策略
## 3. 本源探究：核心源码解析、设计思想溯源
## 4. 版本与特性：主流版本差异、关键特性演进（含弃用与新增）
## 5. 生态与趋势：周边生态集成、技术发展方向（短期/长期）
## 6. 场景化实践：不同业务场景的适配策略与最佳实践
``````

`````` markdown
# $技术指北

## 目的 
- 根据提供的模版进行框架相关内容的系统性输出，需反复确认保证内容正确性，并在 **mcpserver（官方文档、Git 仓库、技术博客等权威数据源）** 以及 **context7（个人/本地知识库向量存储）** 的结合下，保证内容准确可用  
- 在输出前进行交叉验证，至少复盘 5 次论证其可行性，避免错误传播

## 说在前面(README)
- 输出内容需满足 **Typora(1.12.1 (7516))** 的 Markdown 兼容性，特别是 **Mermaid version 11.9**  
- 各级标题不宜过长，避免冗余  
- 内容保持中文输出，非canvas输出亟直接在对话窗口输出（内容过长时可分段，通过“继续”提示补全）  
- 对比说明时优先选取 **市占率最高或最常见的方案** 进行横向比较  
- 涉及 **Mermaid 图表** 时需保证阅读友好，避免图形过大导致排版混乱  
- 遇到 `/-/` 注释内容时，需在输出时进行补充或调整  
- 涉及流程类主题时：
  - 同时提供 **文字化步骤**（1.x、2.x…）与 **Mermaid 流程图/时序图** 双重输出  
  - sequenceDiagram 中需标注 1、2、3 顺序，增强可读性  
- 输出标点统一为半角

## 用途
- 适用于个人总结与系统性学习  
- 重点覆盖 **生产实践 / 面试高频 / 高价值场景**，确保能应对复杂问题与实战场景  

## 数据源使用规则
1. **权威数据源（mcpserver）**  
   - 用于检索官方文档、社区博客、GitHub 项目说明  
   - 示例：`mcpserver.[技术名].docs("调度机制")`  
2. **知识库向量存储（context7）**  
   - 用于存放个人总结、学习笔记、过往经验  
   - 示例：`context7.vectorstore("已有抽象模型总结")`  
3. **策略**  
   - 优先使用 mcpserver 校验事实 → 再结合 context7 进行补充 → 最终输出综合结果
``````
